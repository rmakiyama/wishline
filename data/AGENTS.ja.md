# data

保存された記録をドメインの型に変えるリポジトリ。feature と usecase のモジュールはストレージを見ない。データベースを組み立てるのは `:shared` の依存グラフ。

集約の形をしていない問いには queries（`SQLDelightWishQueries`）が答える。Wish が一度でもカードに乗ったか、のようにテーブルをまたぐ事実は、それを要するクエリの SQL の中で出す。画面が判断に使うものが1回の emit に揃うようにするため。

## 状態と履歴

現在の状態は専用のテーブルからそのまま読む。イベントから導出はしない。Home は開いているすべてのカードの全マスを描くので、その読み取りは素直なクエリのままにする必要がある。

`wish_status_change` と `wish_title_change` は追記だけで、Wish が持ったすべての状態とタイトルを、取り消されたものも含めて残す。まだ読む場所は無い。将来の履歴表示と分析のために置いてある。

- Wish の状態やタイトルの変更は、イベントの書き込みと現在の状態の更新を1トランザクションで行う
- カードにはイベントテーブルが無い。作成・クローズ・ラベル変更はカード自身の行だけを触る
- 履歴テーブルを足すのは、その値の並びがあとで意味を持つときだけ。可変なフィールドすべてに作らない

## クローズしたカードが保つもの

クローズするとマスが動かなくなるので、そのとき付いていたマークは固定される。それ以外はタイトルを含めて、今の Wish から読む。

## SQLDelight

スキーマの ER 図は `.sq` の隣、`src/commonMain/sqldelight/com/rmakiyama/wishline/data/db/AGENTS.md` にある。

- クエリの mapper オーバーロード（`selectAll(::toWish)`）を使い、生成された行クラスを経由せずにドメインの型へ変換する
- `asFlow()` はクエリが名前を挙げたテーブルのいずれかが変わると再発火する。JOIN や副問い合わせを Kotlin 側に移すとその集合からテーブルが抜け、画面が無言で更新されなくなる
- Flow のテストは変更をまたいで collect し続けて確認する
- `.sq` は `sqlite-3-18` の dialect でコンパイルされる。それより新しい構文は、端末が対応していてもパースに失敗する
- 部分インデックスは他のテーブルを参照できないので、テーブルをまたぐ規則は Kotlin 側に置く
- 参照整合性は DB の仕事。外部キーを Kotlin で再検査しない
- SQLite は接続が求めたときだけ外部キーを強制する。各 `DatabaseDriverFactory` とテスト用ドライバで有効にしている。ドライバを足すときも同じ
